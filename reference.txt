Build a production-quality, responsive **MCQ Quiz Platform** using the following stack:

* **Next.js** (App Router, TypeScript)
* **Tailwind CSS**
* **PostgreSQL hosted on Neon**
* **Prisma ORM**
* Authentication with secure role-based access
* Neon Object Storage for question images where appropriate

## 1. Project Goal

Build an online MCQ platform for approximately:

* 20 teams
* Maximum ~25 concurrent users
* Multiple administrators
* Multiple quizzes stored in the system
* Only **one quiz active for users at a time**
* All users participating in an active quiz receive the same quiz
* Quiz can be scheduled using a start time and end time

The system should be simple, reliable, fast, and easy to maintain. Do not introduce unnecessary microservices, Redis, Kafka, Kubernetes, or other infrastructure.

---

## 2. Quiz Structure

Each quiz contains sections.

Example:

### Section 1

* 1-mark questions
* Mostly theoretical/conceptual
* 10 questions

### Section 2

* 2-mark questions
* Mostly practical questions
* May contain:

  * Code snippets
  * Images
  * Output-based questions
  * Technical scenarios
* 20 questions if the total quiz needs to be 50 marks

Important:
Do not hardcode the number of questions or marks. Store section/question marks in the database so administrators can configure them.

Every question has exactly 4 options and exactly one correct option.

## 4. Quiz Lifecycle

Implement:

DRAFT → SCHEDULED → ACTIVE → COMPLETED

A quiz should have:

* title
* description
* start time
* end time
* optional duration
* status
* created_at
* updated_at

The backend must determine whether a quiz is active based on server time.

Do not trust the browser clock.

Only one quiz can be ACTIVE at a time.

Prefer scheduled start/end times over a simple ON/OFF toggle, but provide an administrator control to manually activate/deactivate a quiz when necessary.

---

## 5. Database Design

Use PostgreSQL with Prisma.

Create appropriate relational models for:

* User
* Team
* Quiz
* Section
* Question
* Option
* Attempt
* Answer

Use foreign keys and appropriate indexes.

Important constraints:

* Email must be unique
* A user should not have multiple attempts for the same quiz
* A question belongs to one section
* A section belongs to one quiz
* A question has four options
* Only one option is correct

Use transactions where required, especially during final quiz submission and score calculation.

Prefer soft deletion for entities that may be referenced by historical attempts/results.

---

## 6. Quiz Request Flow

Optimize the request flow.

When the user opens the quiz:

GET active quiz

Return:

* quiz metadata
* sections
* questions
* options
* marks
* images/code snippets

Never send correct answers to the client.

When the user selects an answer, maintain local state and periodically persist answers to the backend.

On final submission:

1. Validate the attempt
2. Validate quiz timing
3. Validate submitted answers
4. Retrieve correct answers from the database
5. Calculate score on the server
6. Save the final score
7. Mark attempt as completed
8. Return the result

Never calculate the authoritative score only on the frontend.

---

## 7. Timer

The frontend timer is only for display.

The backend must remain authoritative.

Store:

* started_at
* submitted_at
* quiz end time

Calculate remaining time using server-controlled timestamps.

If the quiz expires, automatically finalize or reject further submissions according to the quiz rules.

Prevent users from manipulating the browser clock or extending the quiz using JavaScript.

---

## 8. Question Types

Initially support a single-choice MCQ model with exactly four choices.

Questions should support:

### Theory

Plain text question.

### Code

Store:

* question text
* programming language
* code snippet

Display code using a readable monospace/code block.

### Image

Store the image externally and keep its URL/reference in PostgreSQL.

Do not store large image binaries directly inside PostgreSQL.

Design the model so additional question types can be added later.

## 16. Performance

Target:

* ~20 teams
* ~25 concurrent users

Optimize for this scale without overengineering.

Use:

* Proper PostgreSQL indexes
